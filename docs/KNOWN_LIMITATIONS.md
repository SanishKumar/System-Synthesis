# Known limitations

- Offline editing is not supported. The UI pauses graph mutations while disconnected instead of claiming an unsent-operation queue.
- Concurrent edits to different fields of one node merge independently; concurrent edits to the same scalar field use Yjs conflict resolution and may not preserve both users' intent.
- PostgreSQL plus Redis multi-instance behavior is implemented and failure-policy tested, but the published latency run is single-process, loopback, and in-memory. There is no multi-host production capacity claim.
- No PostgreSQL is available in the development environment, so the local gate skips every test that needs one. Continuous integration provides a disposable instance, runs the migration and the synchronization contract against it, and fails if those tests skip rather than run — so the migration statements and the compare-and-set SQL are executed on every push, but not by `npm run verify` on a developer machine. Set `TEST_DATABASE_URL` to a scratch database to run them locally.
- Redis-only mode retains its ordered stream and deliberately does not compact without the PostgreSQL-backed distributed snapshot lock.
- Semantic version history requires PostgreSQL. Development memory mode returns an explicit unavailable response for durable checkpoint creation.
- JWTs have expiry but no server-side denylist. Guest JWTs are server-verified identities, not proof of a real human identity.
- Audit records are application records, not an immutable external compliance log.
- The database connection verifies the server's certificate against the roots Node bundles, which is what the hosted provider's chain terminates at. A provider whose root is not bundled needs `DATABASE_CA_CERT`. `DATABASE_SSL_NO_VERIFY=true` restores encryption without verification and is an incident escape hatch, not a configuration: while it is set, anything able to answer for the database's address can read and rewrite every query.
- Architecture rules are explainable lint policies and graph analyses, not universal architectural truth or formal verification.
- SARIF/JSON describe deterministic findings, but rule suppression policy is not yet managed through an organization-wide policy service.
- Docker Compose import accepts one bounded Compose document. It does not evaluate interpolation, includes, extends, profiles, or override-file merging, so an unexpanded `${VAR}` reference to a service is not resolved and produces no edge.
- Exposure findings classify a bind address but cannot see beyond the Compose file. A port bound to a private network address is reported as a warning without knowing whether that network is reachable from outside, and an unexpanded variable is reported as unresolved rather than evaluated. Neither is treated as contained.
- Environment-inferred dependencies require an exact service-name match on a whole value, URL host, or `host:port` host. A service reached through an alias, an external hostname, a rewritten gateway address, or a name assembled at runtime is not detected, and a value that merely happens to equal a service name produces an edge that is not a real dependency. Inferred edges are marked with `inferred` confidence so a reviewer can tell them from declared ones.
- Import version is reported but nothing re-imports automatically. A review extracted by an earlier importer stays as stored until a new pull-request delivery or a manual re-import rebuilds its graphs; re-analysis deliberately does not, because it reuses those graphs. There is no bulk re-import.
- For ingested reviews the import version is self-reported by the Action that performed the extraction. The server never sees the source and cannot verify it, so a caller that misreports its extraction contract will be believed.
- Compose component classification is a documented heuristic based on image/name/ports. A team must review or extend those rules for organization-specific images.
- Terraform import and general infrastructure round-trip conversion are not implemented. Docker Compose and Terraform export still support only the node subset listed by the IR service, and unsupported resources fail explicitly.
- The browser can create, rotate, and revoke repository-scoped ingestion credentials and provide copyable GitHub Actions inputs, but installation remains a manual repository secret/variable/workflow setup rather than a GitHub App flow.
- A `compose-path` that exists at neither commit fails the Action rather than reviewing two empty documents, but a path that exists and is simply the wrong file is still reviewed as configured. The suggestion list covers root-level Compose filenames only; a Compose file in a subdirectory must be configured explicitly.
- Fork pull requests deliberately do not receive the ingestion token and therefore do not create browser-persisted reviews. They still receive deterministic local Action analysis and artifacts where workflow permissions allow it.
- Repository tokens prove possession of a System Synthesis ingestion credential installed for the configured repository; GitHub ownership is not independently verified until a GitHub App or OIDC exchange is implemented.
- The decision check authenticates the application, not the person. Nothing verifies that whoever approved is a repository collaborator, a code owner, or somebody other than the pull request author, so the gate records who clicked within System Synthesis but cannot yet prove they were entitled to. Adequate for reviewing your own repositories; not yet sufficient for enforcing a gate on a team.
- A decision is recorded before it is published to GitHub, and publishing is best effort. If GitHub is unreachable the decision stands and the pull request keeps its previous check. The review shows that the gate has not been delivered and offers a retry, but there is no outbox and no automatic redelivery: someone has to retry, re-decide, or push a new commit. The interface contract is deliberately shaped so an outbox can be added later without changing it.
- Publishing a check run is serialized within one Node process, keyed on the commit the run belongs to. That prevents two overlapping attempts from each creating a gate on the same commit, which is what the current single-instance deployment needs. Running more than one backend instance would reintroduce the duplicate: two processes can both find no existing run and both create one. Scaling out requires moving that lock into PostgreSQL or Redis first. Nothing else about the synchronization record depends on it — the stored state is protected by a compare-and-set in the database, not by this lock.
- Browser reviews are currently owned by one authenticated user. Shared team ownership and an organization-wide policy service are not implemented.
- A review stored by an earlier analyzer is reported as outdated and can be re-analyzed one review at a time, but nothing recomputes automatically and there is no bulk or scheduled re-analysis. The analyzer fingerprint also cannot see a rule whose findings change while its id and severity stay the same — that case depends on `ANALYZER_VERSION` being bumped deliberately.
- Re-analysis reuses the stored canonical graphs, so it reflects current rules applied to the original import. It does not re-read the repository and will not pick up a source change; only a new pull-request delivery or a fresh import does that.
- There is not yet a published immutable Action release. The dogfood workflow isolates the trusted base-commit Action from the PR source; external consumers should pin a reviewed full commit SHA until a release is published.
- Browser review storage retains canonical base/head graphs, policy, report, decisions, and events; it deliberately does not retain the submitted raw Compose source.
- Terraform output is a deterministic supported model, not a guarantee that every generated deployment is secure, cost-effective, or appropriate for a specific provider account.
- The optional LLM explains deterministic findings and can generate a separate draft architecture, but generated text/graphs remain untrusted suggestions.
- The current live benchmark does not measure server CPU, server memory growth, Redis throughput, PostgreSQL latency, TLS, WAN latency, or browser rendering.
- `sharp` is held above the range Next declares for it. Next 15.5 asks for `^0.34.3`, the libvips advisories are fixed in `0.35.0`, and an override resolves it to `0.35.x`. Nothing in this application uses `next/image` or the image optimizer that would exercise it, and the production build and full gate pass on the overridden version, but it is a dependency running outside its declared support window until Next widens the range.
- One development-only advisory is knowingly unfixed: `esbuild` is held at `0.27.7` by the ranges `vite` and `tsx` declare, and the advisory concerns arbitrary file reads by esbuild's own development server on Windows. Nothing here runs that server — esbuild is reached only as the transform step inside Vitest and tsx — and forcing a minor bump inside Vite's pinned range risks breaking the test runner for no reduction in exposure. It carries no production risk: `npm audit --omit=dev` reports zero vulnerabilities.
- Deployment to Cloudflare Workers/Sites is not configured. The backend depends on a long-running Socket.IO process and would require an explicit hosting/runtime migration.
