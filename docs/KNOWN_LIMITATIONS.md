# Known limitations

- Offline editing is not supported. The UI pauses graph mutations while disconnected instead of claiming an unsent-operation queue.
- Concurrent edits to different fields of one node merge independently; concurrent edits to the same scalar field use Yjs conflict resolution and may not preserve both users' intent.
- PostgreSQL plus Redis multi-instance behavior is implemented and failure-policy tested, but the published latency run is single-process, loopback, and in-memory. There is no multi-host production capacity claim.
- No PostgreSQL is available in the development environment, so the local gate skips every test that needs one. Continuous integration provides a disposable instance, runs the migration and the synchronization contract against it, and fails if those tests skip rather than run — so the migration statements and the compare-and-set SQL are executed on every push, but not by `npm run verify` on a developer machine. Set `TEST_DATABASE_URL` to a scratch database to run them locally.
- Redis-only mode retains its ordered stream and deliberately does not compact without the PostgreSQL-backed distributed snapshot lock.
- A configured Redis that will not connect degrades the instance to memory rather than stopping it. Health reports `redis: failed` with the reason, and returns 503 in production so a platform can refuse the deploy, but the process keeps serving: whether that is preferable to an outage is the operator's decision, not this service's. While degraded, each instance holds its own copy of state that is meant to be shared, so cross-instance collaboration is not happening.
- A Redis connection that drops after a successful start is recovered automatically, and the reported state follows it down and back up. A Redis that was never reachable at startup is not retried in the background: the Socket.IO adapter and the collaboration subscriber are built during startup, so a connection arriving afterwards would be held by nobody and would fan out to nothing. Recovery from a failed start is a restart, which is what reporting 503 asks the platform to do.
- Semantic version history requires PostgreSQL. Development memory mode returns an explicit unavailable response for durable checkpoint creation.
- The signed state that carries a GitHub authorisation is expiring and bound to the account that started it, but it is not single-use: nothing consumes it, so the same state stays valid for its ten-minute window. What limits a replay in practice is GitHub's authorisation code, which GitHub itself spends on first exchange. Making the state one-time needs a consumed nonce or a browser-bound session, and neither is implemented.
- JWTs have expiry but no server-side denylist. Guest JWTs are server-verified identities, not proof of a real human identity.
- Audit records are application records, not an immutable external compliance log.
- The hosted frontend reports page traffic to Vercel Web Analytics: how many people arrive, from where, and which routes they open. It is cookieless, but it is not identifierless: Vercel derives a visitor hash from the incoming request that lasts a day, so the accurate word is anonymous. Whether a given jurisdiction requires consent for that is a question for whoever operates the deployment. Review identifiers, board identifiers and invitation tokens are stripped from the URL, along with its query, before it is sent, so the record reads `/reviews/[id]`. Nothing about a review's contents, findings or decisions is sent. A self-hosted deployment that does not want this should remove the component from the root layout; there is no runtime switch.
- Database and Redis connections verify the server's certificate against the roots Node bundles, which is what both hosted providers' chains terminate at. A provider whose root is not bundled needs `DATABASE_CA_CERT` or `REDIS_CA_CERT`. The matching `_SSL_NO_VERIFY` variables restore encryption without verification and are incident escape hatches, not configuration: while one is set, anything able to answer for that address can read and rewrite every request.
- Transport security is decided from the host, not the URL scheme. Only loopback is treated as needing no encryption; a container on a private network is not, so the Docker development stack states `sslmode=disable` explicitly. That is a deliberate trade: a host-based rule cannot tell a trusted private network from an untrusted one, so it asks rather than assumes, and a new deployment that forgets to say gets a failed TLS negotiation rather than silent plaintext.
- Plaintext to a non-loopback host is refused in production unless `DATABASE_ALLOW_PLAINTEXT` or `REDIS_ALLOW_PLAINTEXT` is set. The refusal is enforced at startup from the connection string; it cannot detect a proxy or tunnel that terminates TLS elsewhere, so an operator who genuinely has one still has to say so.
- Architecture rules are explainable lint policies and graph analyses, not universal architectural truth or formal verification.
- SARIF/JSON describe deterministic findings, but rule suppression policy is not yet managed through an organization-wide policy service.
- Docker Compose import accepts one bounded Compose document. It does not evaluate interpolation, includes, extends, profiles, or override-file merging, so an unexpanded `${VAR}` reference to a service is not resolved and produces no edge.
- Exposure findings classify a bind address but cannot see beyond the Compose file. A port bound to a private network address is reported as a warning without knowing whether that network is reachable from outside, and an unexpanded variable is reported as unresolved rather than evaluated. Neither is treated as contained.
- Environment-inferred dependencies require an exact service-name match on a whole value, URL host, or `host:port` host. A service reached through an alias, an external hostname, a rewritten gateway address, or a name assembled at runtime is not detected, and a value that merely happens to equal a service name produces an edge that is not a real dependency. Inferred edges are marked with `inferred` confidence so a reviewer can tell them from declared ones.
- A graph stored by an importer that recorded different fields makes no claim about what it did not record. A Kubernetes graph from importer version 1 carries `selectedByNetworkPolicy` and no per-direction coverage, and that flag cannot be converted into one: version 1 counted an egress-only policy and read a `matchExpressions` selector as selecting a whole namespace. Both NetworkPolicy findings stay silent on such a graph rather than guessing in either direction, and import staleness remains the signal that the source needs delivering again.
- Import version is reported but nothing re-imports automatically. A review extracted by an earlier importer stays as stored until a new pull-request delivery or a manual re-import rebuilds its graphs; re-analysis deliberately does not, because it reuses those graphs. There is no bulk re-import.
- For ingested reviews the import version is self-reported by the Action that performed the extraction. The server never sees the source and cannot verify it, so a caller that misreports its extraction contract will be believed.
- Compose component classification is a documented heuristic based on image/name/ports. A team must review or extend those rules for organization-specific images.
- The Kubernetes adapter is available in `architecture-core` but is not yet reachable from the CLI, the Action, or the server, all of which still import Docker Compose. Adapter selection is the next piece of work; until it lands, a Kubernetes repository cannot be reviewed through any shipped entry point.
- Helm charts are detected and refused rather than rendered. A chart is Go template source in which a conditional decides whether a resource exists at all and a range decides how many there are, so reading one as YAML would assert a topology the source never stated. This is not a small gap: Helm is how a large share of projects declare their production topology, and for those repositories the adapter reports that it found a chart instead of producing a graph.
- A Kustomize base is read as the plain manifests it contains, but `kustomization.yaml` is not evaluated. Name prefixes, namespace overrides, replica counts, image tags, and patches applied by an overlay are not reflected, so the graph describes the base rather than what any particular overlay would apply.
- Reach is decided from Service type, `externalIPs`, and Ingress backends. A LoadBalancer made internal by a cloud provider annotation is still reported as external, and an Ingress controller's own reachability is assumed rather than read. A Service type the import cannot resolve is recorded as unresolved and treated as reaching outside, never as contained.
- NetworkPolicy coverage records whether a policy governs traffic into a workload, not what that policy then permits. A policy that selects a pod and allows every source still counts as inbound coverage, so the finding says a workload is ungoverned rather than unprotected. Set-based `matchExpressions` selectors are not evaluated: a policy using one is recorded as `unknown` coverage for every workload in its namespace, never as covering them, and raises a separate finding saying coverage could not be established. That is deliberately conservative — one such policy makes its whole namespace unknown, which is a weaker signal than a confirmed gap but never a false assurance.
- Kubernetes dependencies are inferred from literal container environment values, arguments, and commands that name a Service in the same namespace. Addresses that arrive through a ConfigMap or Secret reference, service discovery, a CRD, or an operator are not detected. Real manifest sets frequently contain none of the literal form: importing kube-prometheus produces components with no relationships between them, which is a true statement about what its manifests declare rather than about how it runs.
- Custom resources are not understood. A workload created by an operator from a CRD — a Prometheus, a Rollout, a database cluster — is invisible to the import, so a manifest set that delegates its topology to operators yields fewer components than it runs.
- A manifest that names no namespace is read as `default`, which is what `kubectl` does without `-n`. A repository that relies on the applying command or an overlay to choose the namespace will have its resources grouped under `default`, and Services will not match workloads across that boundary.
- Terraform import and general infrastructure round-trip conversion are not implemented. Docker Compose and Terraform export still support only the node subset listed by the IR service, and unsupported resources fail explicitly.
- The browser can create, rotate, and revoke repository-scoped ingestion credentials and provide copyable GitHub Actions inputs, but installation remains a manual repository secret/variable/workflow setup rather than a GitHub App flow.
- A `compose-path` that exists at neither commit fails the Action rather than reviewing two empty documents, but a path that exists and is simply the wrong file is still reviewed as configured. The suggestion list covers root-level Compose filenames only; a Compose file in a subdirectory must be configured explicitly.
- Fork pull requests deliberately do not receive the ingestion token and therefore do not create browser-persisted reviews. They still receive deterministic local Action analysis and artifacts where workflow permissions allow it.
- Connecting a repository requires admin permission on it, confirmed with GitHub through the App and compared against the linked account's immutable numeric id. Admin rather than write, because the credential makes the App publish checks on that repository. Authority is established again when the stored proof is more than an hour old, so a credential outlives lost access by at most that long; confirming on every ingestion would put a GitHub call on the hot path of every push and make a rate limit an outage. A revalidation that cannot be completed refuses the ingestion rather than publishing, so a GitHub outage lasting longer than the interval stops ingestion for the repositories whose proof went stale during it.
- Credentials issued before repository authority was checked are refused. They carry no proof, nothing stored can establish that they were ever legitimate, and no attempt is made to infer it — their owners reconnect once, which re-issues the credential and proves admin. Any automation holding an older token fails with `integration_unverified` until it is replaced.
- Repository tokens prove possession of an ingestion credential issued for the configured repository. Ingestion re-checks GitHub only when the stored proof has gone stale, so within that window the credential is the authority; protect and rotate it accordingly. A revalidation that GitHub refuses is not retried for a minute, so restoring access takes effect up to that long afterwards, and the lookup is shared across concurrent deliveries within one server process — a multi-instance deployment performs at most one per instance per interval.
- Entitlement is checked only where the deployment can check it. A server configured with both the App and reviewer identity requires a linked GitHub account with write access to the repository, and refuses the pull request's own author; a server missing either is recorded as deciding without verification rather than being locked out. That means the same decision carries different weight on differently configured deployments, and the record says which: every decision stores the basis it was allowed on, and a verified one also stores the GitHub account id that decided, the login GitHub resolved at the time, the permission level it reported, and when it was asked. The evidence is written in the same transaction as the decision, so a decision cannot exist without it.
- Code ownership is not consulted. Write access to the repository is the bar, so a collaborator who owns no part of the changed architecture can still decide. `CODEOWNERS` is not read.
- Permission is read at the moment of the decision and not retained. A decision made by someone who later loses access stays recorded as it was, which is the honest account of what happened but is not a continuing assertion that they still have standing.
- A decision is recorded before it is published to GitHub, and publishing is best effort. If GitHub is unreachable the decision stands and the pull request keeps its previous check. The review shows that the gate has not been delivered and offers a retry, but there is no outbox and no automatic redelivery: someone has to retry, re-decide, or push a new commit. The interface contract is deliberately shaped so an outbox can be added later without changing it.
- Publishing a check run is serialized within one Node process, keyed on the commit the run belongs to. That prevents two overlapping attempts from each creating a gate on the same commit, which is what the current single-instance deployment needs. Running more than one backend instance would reintroduce the duplicate: two processes can both find no existing run and both create one. Scaling out requires moving that lock into PostgreSQL or Redis first. Nothing else about the synchronization record depends on it — the stored state is protected by a compare-and-set in the database, not by this lock.
- Browser reviews are currently owned by one authenticated user. Shared team ownership and an organization-wide policy service are not implemented.
- A review stored by an earlier analyzer is reported as outdated and can be re-analyzed one review at a time, but nothing recomputes automatically and there is no bulk or scheduled re-analysis. The analyzer fingerprint also cannot see a rule whose findings change while its id and severity stay the same — that case depends on `ANALYZER_VERSION` being bumped deliberately.
- Re-analysis reuses the stored canonical graphs, so it reflects current rules applied to the original import. It does not re-read the repository and will not pick up a source change; only a new pull-request delivery or a fresh import does that.
- There is not yet a published immutable Action release. The dogfood workflow isolates the trusted base-commit Action from the PR source; external consumers should pin a reviewed full commit SHA until a release is published.
- Browser review storage retains canonical base/head graphs, policy, report, decisions, and events; it deliberately does not retain the submitted raw Compose source.
- Terraform output is a deterministic supported model, not a guarantee that every generated deployment is secure, cost-effective, or appropriate for a specific provider account.
- The optional LLM explains deterministic findings and can generate a separate draft architecture, but generated text/graphs remain untrusted suggestions.
- The current live benchmark does not measure server CPU, server memory growth, Redis throughput, PostgreSQL latency, TLS, WAN latency, or browser rendering.
- `sharp` is held above the range Next declares for it. Next 15.5 asks for `^0.34.3`, the libvips advisories are fixed in `0.35.0`, and an override resolves it to `0.35.x`. Nothing in this application uses `next/image` or the image optimizer that would exercise it, and the production build and full gate pass on the overridden version, but it is a dependency running outside its declared support window until Next widens the range.
- Deployment to Cloudflare Workers/Sites is not configured. The backend depends on a long-running Socket.IO process and would require an explicit hosting/runtime migration.
